# Training Platform Sprint 1

## Objective

Sprint 1 creates the first production-grade layer of a local-first model platform for Jester. The goal is not to ship a fine-tuned production model. The goal is to make future training safe, repeatable, auditable, and backend-compatible.

## Why local-first

Jester already separates deterministic application logic from language generation. A local-first model strategy extends that architecture with four practical benefits:

- predictable operating cost for narration, teaching, and prep-heavy workloads
- private iteration on task-specific adapters, prompts, and evaluations
- tighter observability and version control over the exact model/runtime used
- the option to operate without a cloud dependency for supported workloads

Local-first does not mean the model owns the product. It means the backend can call a locally served model as one backend dependency among several.

## What "proprietary model" means for Jester

In this repository, a proprietary Jester model does not mean training a foundation model from scratch. It means the deployable intelligence stack is proprietary because Jester owns or governs the pieces that matter to product behavior:

- source-governed datasets and manifests
- private adapters, finetunes, and eval sets
- task-specific contracts and safety requirements
- backend orchestration logic, retrieval assembly, and routing policy

The base weights may be open-weight. The Jester-specific artifacts layered on top are private and versioned.

## Why open-weight bases plus private adapters

Training from scratch is the wrong optimization for Sprint 1 and likely the wrong one for the near-term product roadmap. Jester needs:

- commercially usable local bases
- role specialization for prose, reasoning, and routing
- repeatable adaptation on governed corpora
- rapid evaluation against backend tasks

Open-weight bases plus private adapters and datasets satisfy those goals without the capital cost, data volume, or operational risk of pretraining.

## Responsibility split

### Backend remains authoritative for

- request validation and auth
- session handling and state integrity
- retrieval orchestration and context assembly
- permissions, safety gates, and fallbacks
- deterministic rules and game-state logic
- persistence, observability, and version resolution
- selecting whether a request should invoke a model at all

### Local models become responsible for

- narration generation
- prep generation
- teaching explanations
- rules reasoning support from retrieved context
- routing and classification assistance
- response drafting grounded in backend-supplied context

This preserves the current Jester architecture: language is generated by models, but truth remains in deterministic services and retrieved artifacts.

## Backend tasks that are model-backed

The local model layer exists to support concrete backend tasks, not vague general intelligence:

- `Prep`: encounter ideas, setting details, quest hooks, NPC summaries, worldbuilding expansions
- `Teaching`: explanations, walkthroughs, misconception handling, examples, practice prompts
- `Live DM`: scene narration, sensory detail, NPC voice drafts, consequence framing
- `Rules reasoning support`: likely interpretation, rationale, confidence, citation targets from retrieved rules context
- `Routing/classification`: task family, response style, depth, and workspace intent

## Backend tasks that remain deterministic

The following stay outside model authority even after local runtime integration:

- canonical combat and session state mutation
- rule-bound action legality checks
- persistence and revision control
- retrieval index selection and provenance filtering
- permission checks and safety policy enforcement
- artifact versioning and release management

If the local model disagrees with deterministic state or rule engines, the backend wins.

## Operational definition of legally safe

For Sprint 1, a source is legally safe only when all of the following are true:

- the source has a machine-readable manifest
- ownership, license, and rights basis are explicit
- the source is classified into one of four policy categories: `train_and_rag`, `rag_only`, `reference_only`, or `blocked`
- a reviewer has assigned a review status
- the source has a removal contact or a documented reason why removal is not applicable
- a stable content hash exists for traceability and duplicate detection
- downstream records inherit the source eligibility rather than overriding it

Anything unclear, scraped without permission, or missing legal metadata is blocked or quarantined.

## Sprint 1 runtime target

The runtime target for this sprint is a stable contract, not a full Ollama deployment. The backend should be able to speak to a future local model runtime through a provider-neutral request and response envelope:

```text
Website
  -> Jester Backend API
      -> Application Services
          -> Retrieval / Context Assembly
          -> Task Router
          -> Local Model Runtime Contract
              -> Future Ollama-served role models
```

The backend will continue to:

- choose the task family and role
- assemble retrieval context
- set hard constraints such as max tokens, citation requirements, and structured-output mode
- validate or discard model output

The local runtime will eventually:

- map the role to a concrete local model
- run the prompt against the provider
- return a normalized response envelope
- surface runtime warnings, latency, and provider metadata

## Role strategy

Sprint 1 defines three future role models:

- `Narrator`: prose-heavy prep and live narration
- `Arbiter`: rules reasoning and teaching explanations
- `Router`: small-fast classification and orchestration hints

This role split is preferable to one monolithic model because each workload has different latency, context, and output-shape requirements.

## Enforcement model

Sprint 1 introduces hard gates before any future training export:

1. Every candidate source requires a validated source manifest.
2. Missing or ambiguous ownership, license, or rights basis blocks approval.
3. Duplicate content hashes and conflicting manifest states are rejected.
4. Training records must reference an approved source manifest.
5. Record-level `allowed_for_training` and `allowed_for_rag` flags cannot exceed source-level permissions.

These controls are intentionally strict. The cost of blocking a questionable source is lower than the cost of poisoning the corpus.

## Exit criteria for the sprint

Sprint 1 is successful when the team can answer these questions with artifacts in the repo rather than discussion alone:

- What does the local model do for Jester?
- What still belongs to the backend?
- Which source categories are legally safe for training?
- How is every training record traced back to a reviewed source?
- What request and response contract will the backend use for a future local runtime?

Sprint 2 can then focus on dataset builders, evaluations, and runtime integration on top of a governed foundation.
